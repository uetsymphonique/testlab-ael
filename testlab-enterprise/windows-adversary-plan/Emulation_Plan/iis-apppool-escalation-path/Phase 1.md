# Phase 1 - Initial Access & Command and Control

## Overview
The attacker targets an internal IIS server hosting `react.testlab.local`. A React Server Components deserialization vulnerability (CVE-2025-55182) is exploited to achieve unauthenticated RCE on the IIS server as `IIS APPPOOL\react.testlab.local`. From this foothold, the react2shell staging channel delivers two disk-resident artifacts — the EfsPotato escalation tool and an XOR-encoded dnscat2 DnsQuery_W payload (`cmd/dnscat-dnsapi`) — then delivers the CWLHerpaderping loader via stdin pipe into the EfsPotato process, escalating to `NT AUTHORITY\SYSTEM` and establishing a DNS C2 session as a ghost `RuntimeBroker.exe` process.

## Step 1 — Initial Access & Payload Staging

### Voice Track

The attacker exploits `react.testlab.local` — a Next.js application running under `iisnode` on the IIS server. A crafted React Server Components multipart request reaches the vulnerable deserialization path and executes JavaScript inside the Node.js worker as `IIS APPPOOL\react.testlab.local`.

With the web RCE shell live, two artifacts are staged to disk via the react2shell in-memory base64 stream. The dnscat2 payload is staged with `--encrypt`: position-dependent XOR (`out[i] = in[i] ^ ((0xA3 + i*0x5B) & 0xFF)`) is applied in Python memory before encoding, writing `C:\ProgramData\CertCA.enc` — the on-disk file carries no valid MZ header (first byte `0xEE` instead of `0x4D`), defeating file-hash and byte-signature detections (T1027.013). The EfsPotato escalation tool is staged without encryption to `C:\Windows\Temp\CertEnrollSvc.exe`. Neither staging operation writes a `.b64` intermediate to disk at any point.

> Further reading: [rce-react2shell.md](../further-reading/rce-react2shell.md) covers the exploit tool and staging flow.

## Step 2 — Privilege Escalation via EfsPotato

### Voice Track

With both artifacts staged, the attacker delivers the CWLHerpaderping loader as raw PE bytes streamed directly into `CertEnrollSvc.exe`'s stdin pipe via a single `spawnSync` call. `CertEnrollSvc.exe` reads the loader PE from stdin, then exploits `SeImpersonatePrivilege` — held by the IIS AppPool identity — through a named-pipe impersonation sequence: it creates a named pipe, triggers an EFS RPC call to force a privileged SYSTEM-context process to connect, and executes `NtFsControlFile(FSCTL_PIPE_IMPERSONATE)` + `NtOpenThreadToken` + `NtDuplicateToken` via indirect syscall trampolines to capture a SYSTEM primary token. All Win32 delegates are resolved at runtime via `GetProcAddress` using XOR-decoded name strings (`S()` decode + `R<T>()` resolution pattern), leaving a sparse import table with no plaintext API names. The SYSTEM token is then used to spawn the CWLHerpaderping loader via `CreateProcessWithTokenW` (Secondary Logon service path), routing through the secondary logon service to avoid `ERROR_ACCESS_DENIED` from the limited-caller IIS AppPool context.

> Further reading: [efspotato.md](../further-reading/efspotato.md) covers `CertEnrollSvc.cs`.

### Procedures

## Step 3 — Process Herpaderping

### Voice Track

Running as `NT AUTHORITY\SYSTEM`, the CWLHerpaderping loader executes a fully automatic chain requiring no further operator interaction. On startup, it patches `ntdll!EtwEventWrite` in its own address space (when compiled with `ENABLE_ETW_PATCH`) and resolves all NT API addresses via hash-based lookup. It then reads `CertCA.enc` from disk, XOR-decodes the dnscat2 payload entirely in-process (self-inverse formula matching `PAYLOAD_XOR_BASE`/`PAYLOAD_XOR_STEP` constants), and immediately deletes `CertCA.enc` to remove the staged artifact. The decoded PE is written into a hidden `HD*.tmp` section-backed image file (`FILE_ATTRIBUTE_HIDDEN`), and a ghost process is created using `NtCreateUserProcess` with `RTL_USER_PROCESS_PARAMETERS` specifying `C:\Windows\System32\RuntimeBroker.exe` as the image path. Before the `NtCreateUserProcess` syscall, a `kernel32.dll` `add rsp,28h; ret` gadget address is planted on the current thread stack to make the EDR call-stack view show `kernel32.dll` as the syscall origin. The ghost process is PPID-spoofed to a Session 0 `svchost.exe` or `wininit.exe` via `PS_ATTRIBUTE_PARENT_PROCESS`. After the process is created with its primary thread suspended, the loader overwrites `HD*.tmp` in-place with IIS W3SVC log decoy content — destroying the on-disk PE while the ghost process retains the original section-backed mapping. The primary thread is then resumed.

> Further reading: [process-herpaderping.md](../further-reading/process-herpaderping.md) covers CWLHerpaderping.

### Procedures

- Wait for the CWLHerpaderping chain to complete — the loader executes automatically inside the SYSTEM child process spawned by CertEnrollSvc.exe; no operator action is required for this step; the chain exits after resuming the ghost thread, and a new dnscat2 session appears on the attacker machine (confirmed in Step 4)

## Step 4 — DNS C2 Establishment

### Voice Track

The ghost `RuntimeBroker.exe` process, now executing the dnscat2 DnsQuery_W payload as `NT AUTHORITY\SYSTEM`, enumerates DNS resolver configuration from the registry (`HKLM\SYSTEM\CurrentControlSet\Services\Tcpip\Parameters\Interfaces\<GUID>\NameServer`) and establishes an encrypted DNS C2 tunnel. The DnsQuery_W transport variant routes all DNS queries through `dnsapi.dll!DnsQuery_W`, so the UDP/53 socket is held by `svchost.exe` running the Dnscache service rather than by the ghost process — at the network layer, tunnel traffic appears to originate from a trusted Windows system service. Sysmon Event 22 still logs `RuntimeBroker.exe` as the querying process via its PID, but NDR tools and firewall socket-attribution rules see `svchost.exe`. The attacker confirms the SYSTEM session and issues a `shell` command to spawn `cmd.exe` under the ghost process; all subsequent commands in Phases 2–5 execute within this child shell.

> Further reading: [dnscat2.md](../further-reading/dnscat2.md) covers the DNS C2 client.

### Procedures

- ☣️ Switch to the attacker machine and confirm the SYSTEM C2 session

  ```text
  dnscat2> New session established: <session-id-1>
  dnscat2> session -i <session-id-1>
  command (iis-server) 1> whoami
  ```

  - ***Expected Output***

    ```text
    nt authority\system
    ```

- ☣️ Open an interactive `cmd.exe` shell from the SYSTEM dnscat2 session

  ```text
  command (iis-server) 1> shell
  ```

  - ***Expected Output***

    ```text
    New session created: <session-id-2>
    ```

  ```text
  dnscat2> session -i <session-id-2>
  sh (iis-server) 2>
  ```

  > **Note:** `shell` spawns `cmd.exe` as a child of the `RuntimeBroker.exe` ghost process under `NT AUTHORITY\SYSTEM`. All subsequent commands in Phases 2–5 that run from the IIS01 SYSTEM session execute within this `cmd.exe` child.
